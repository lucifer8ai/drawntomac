## Problem Statement

The website looks good on desktop but feels oversized on mobile. Text is too big, album cards are too big, and the entire interface reads as a desktop design that was responsive-squished rather than built for a phone. The goal is a comprehensive mobile-first redesign across every context — detail pages, feed, discover, navigation, and eventually shareable taste cards.

Target device: iPhone (390×844px viewport), PWA installed on home screen, with a notch and safe areas. The browser tab is secondary.

## What Makes This Cool

A dark, cinematic music journal that feels like a native iOS app when you add it to your home screen. The journal aesthetic means: dense and scannable where you're browsing, editorial and weighty where you're looking at one thing. Album art carries the emotion, typography carries the hierarchy, and nothing feels like a website wearing a phone costume.

The 10x version: every song page, diary entry, and stat card is already designed to look good as a standalone shareable image. Generating a taste card is one tap, not an export pipeline bolted on later.

## Current Mobile Sizing (What's Broken)

| Element | Current Mobile | Issue |
|---|---|---|
| Song title (detail) | `text-3xl` (30px) | Fills half a 390px screen |
| Cover art (detail) | `max-w-[320px]` | Leaves ~35px total margins |
| Cover art radius | `rounded-2xl` (16px) | Fine — keep |
| Artist name (detail) | `text-base` (16px) | Slightly heavy for metadata |
| Feed song titles | `text-base` (16px) | Chunky for scanning a list |
| Feed album thumbnails | `h-14 w-14` (56px) | Combined with 16px text, cards feel oversized |
| Feed card padding | `py-3` (12px vertical) | Room to tighten |
| Discover album cards | `w-[100px]` | Reasonable, but could use tighter metadata |
| Button default | `h-9` (36px) | Fine — 44px touch target respected |
| Input fields | `text-base md:text-sm` | Correct pattern — iOS zoom prevention |

## Viewport Strategy

- **Mobile (390-767px):** Full compact scale — `text-sm` body, 24px titles, 240px cover art, 48px thumbnails. This covers iPhone SE through iPhone Pro Max and most Android phones.
- **Tablet / Large phone (768px+):** Desktop editorial scale restored via `md:` breakpoint. No intermediate breakpoint is needed — the existing editorial scale works from iPad Mini upward.
- **Landscape mobile:** Detail pages keep the stacked layout (no side-by-side until `md:`). Feed cards use `max-w-lg mx-auto` to avoid edge-to-edge stretching. The song page layout stays single-column with centered art — side-by-side only activates at `md:` (768px), which is tablet territory.
- **Desktop (≥768px):** Pixel-identical to current rendering. No visual changes. All mobile overrides are scoped via `@media (max-width: 767px)` or `md:` restorations.

## Accessibility

- **Minimum contrast:** All text sizes down to `text-[10px]` on `oklch(0.58 0.02 85)` foreground over `oklch(0.04 0.002 280)` background — verify 4.5:1 ratio on all reduced-size text during Phase 1.
- **Touch targets:** 44×44px minimum on ALL interactive elements after the shrink — verify every Phase 2 and Phase 3 touch target.
- **Reduced motion:** `prefers-reduced-motion` already drops animations to 0.01ms in `src/styles.css`. Phase 4 swipe gestures MUST degrade to tap-only when reduced motion is active.
- **Screen reader labels:** All icon-only buttons and controls need `aria-label`. Action bar buttons (heard, like, dislike, want, save), bottom nav tabs, search trigger, share button, close buttons. These should already exist from shadcn/ui patterns — verify, don't assume. Add `aria-pressed` to toggle buttons (heard/like/etc.) to communicate on/off state.
- **Focus order:** Verify Tab order on all mobile screens follows visual hierarchy — action bar buttons before review section, discover cards in row order. Modal dialogs (artist picker, edit artists) need focus trap: focus locks inside the dialog, restores to trigger on close. Existing Dialog component from shadcn/ui likely handles this — verify at 390px.
- **RTL readiness:** Not in scope for this redesign. drawnTo has no RTL users yet. When needed, the DM Sans font and flexbox-based layouts will support it, but text alignment and icon mirroring are untested.
- **Verification per phase:** Each phase's verification step includes an a11y audit for contrast, touch targets, screen reader labels, and focus order.

## What's Already Good

- Bottom nav: 20px icons, `text-[10px]` labels — tight and native-feeling
- Horizontal scroll with snap on discover — good mobile UX
- `text-base md:text-sm` on inputs — prevents iOS zoom
- Badges at `text-xs` (12px) — appropriate
- Action colors only appear on interaction — DESIGN.md intact
- DM Sans single-font system with weight contrast — perfect for mobile

## Visual Hierarchy Per Screen

### Song Detail Page (390×844px, first viewport ~600px)

**Priority order** (what the user registers 1st, 2nd, 3rd):
1. **Cover art** (240×240px, centered, 16px border radius) — the emotional anchor. Absorbs ~60% of first-viewport visual weight. Album artwork IS the identity of the page.
2. **Song title** (24px DM Sans bold, near-white) — immediately below art, max 12px gap. Confirms "this is the right song." The title + art pair should read as one unit.
3. **Action bar** — row of 5 buttons (heard/like/dislike/want/save), 44×44px touch targets, fixed at the bottom of the viewport (above the bottom nav). This is what users DO on this page. Extracted from the scrollable content into a sibling element — content scrolls behind it, actions always reachable. Matches native iOS/Android app patterns.
4. **Artist name** (14px, warm near-white) — secondary context, useful after identity is established.
5. **Release date + genre tags** — tertiary metadata, 12px, subdued warm grey.
6. **Review section** — below the fold, scroll to discover. Text area + submit button.
7. **Related songs** — further below, scroll to discover. List with 48px thumbnails.

**Sticky behavior:** The action bar should remain visible during scroll (sticky below the header or at a natural anchor point). Users scroll to read reviews, not to find the "heard" button again.

### Feed Timeline (390×844px, infinite scroll)

**Priority order:**
1. **Card content** (song title 14px bold + action badges) — the thing users scan. Each card should be scannable in <1 second.
2. **User identity** — avatar (28px) + display name at card top. "Who did this?"
3. **Album thumbnail** (48×48px, right-aligned) — visual confirmation, supports but doesn't dominate the card.
4. **Timestamps + metadata** — 12px, subdued. Important but last in scan order.

**Scan pattern:** Users scan the feed top-to-bottom, stopping on cards with familiar names or interesting actions. A card should communicate: who, did what, to what song — all in the first 200ms of attention.

### Discover Feed (390×844px, horizontal scroll sections)

**Priority order:**
1. **Artist name** (12px, section header) — scannable left-aligned. "Whose albums are these?"
2. **Album art** (88×88px square, 16px radius) — the visual bait. Horizontal scroll with snap.
3. **Album title** (12px, below art) — confirmatory, secondary to art.

**Scan pattern:** Vertical scroll through artist sections, then horizontal scroll within each section. Two-axis scroll is deliberate — artists are the browsing axis, albums are the discovery axis.

### Diary Tab (390×844px, personal listening log)

**Priority order:**
1. **Song title** (14px bold) — "What did I listen to?"
2. **Action badges** (heard/liked/reviewed/want, 12px with icons) — "What did I do with it?"
3. **Album thumbnail** (48×48px, left-aligned) — visual reminder, supports the title.

**Difference from feed:** Diary is personal and scannable for recall, not social discovery. No usernames, no avatars — just your own listening history.

### Album / Artist / User Detail Pages

Same hierarchy as song page with swapped primary media: album cover art, artist hero/avatar, or user avatar as the emotional anchor. Title + metadata follow the same 1-2-3 pattern.

## User Journey & Emotional Arc

Three core mobile journeys define whether drawnTo feels like a journal or a website.

### Journey 1: Cold Open — First Listen Log (5-second visceral, 5-minute behavioral)

| Step | User Does | User Feels | Design Supports |
|---|---|---|---|
| 1. Open PWA | Taps drawnTo icon on home screen | Anticipation — no browser chrome, just the app. Feels like a real thing | `display: standalone`, `black-translucent` status bar. No URL bar, no refresh button. The app shell is the whole screen |
| 2. Land on feed | Sees activity from people they follow | Belonging — "people I know are here" or curiosity — "what is this place?" | Feed cards at the new 14px density. 4-5 cards visible without scrolling. Scannable rhythm |
| 3. Tap bottom nav to Discover | Explores new music | Discovery — "what should I listen to?" | Artist sections with horizontal album scroll. 88px cards — small enough to show 4 per row, large enough to recognize art |
| 4. Tap an album | Views album detail at 390px | Focus — art-centered, title prominent, tracklist scannable | 240px cover art, 24px title, stacked layout. Album context is clear |
| 5. Tap a song | Song detail page | Commitment — "I want to log this" | Cover art confirms the song, action bar is immediately below. The "heard" button is the most visible action |
| 6. Tap "heard" | First listen logged | Satisfaction — the button fills green, haptic pulse. Something happened | Green 15% background fill, active:scale-[0.97] press feedback. If `navigator.vibrate` available (Phase 5): 10ms haptic blip |
| 7. Scroll down | Reads related songs, maybe logs more | Exploration — "what else is here?" | Related songs with 48px thumbnails. Same familiar card pattern from feed |

**5-second test:** User opens the PWA and immediately knows: this is a music app, this is a dark personal space, I can scroll and tap things.

### Journey 2: Daily Scroll — The 5-Minute Ritual

| Step | User Does | User Feels | Design Supports |
|---|---|---|---|
| 1. Opens PWA on commute | Muscle memory tap | Habit — this is part of the routine | Feed loads at 14px density. 4-5 cards fill the screen. Quick scan reveals what friends listened to |
| 2. Scrolls feed | Scans entries, stops on interesting ones | Social connection — "Sam liked that song too" | CoalescedCard shows avatar stack + action badges. The "who" + "what" + "action" pattern is scannable in <1s per card |
| 3. Switches to Diary tab | Checks own listening history | Self-reflection — "what was I into last week?" | Diary at 14px, scannable list of own actions. Badges show heard/liked/reviewed at a glance |
| 4. Taps a song from diary | Revisits a past listen | Nostalgia — "I remember this" | Song page loads. Cover art, title, the action badges already filled. "You listened to this 3 days ago" |
| 5. Logs another listen | Taps "heard" again on the same song | Reinforcement — "this song is part of my identity now" | Button toggles. Already-green state is clear. Haptic feedback confirms action |

**The emotional throughline:** Social connection (feed) → self-reflection (diary) → re-engagement with music (song page). The app facilitates this loop without forcing it.

### Journey 3: The Share Moment

| Step | User Does | User Feels | Design Supports |
|---|---|---|---|
| 1. Finds a song they love | On the song page, looking at a song with multiple badges | Pride — "this song represents my taste" | Song page is already designed as a shareable rectangle. Cover art + title + badges form a balanced composition |
| 2. Taps the share icon | Contextual share button in the song header row | Anticipation — "someone needs to see this" | Share button is subtle but findable. Not a floating FAB — it's in the header row with back and other controls |
| 3. Sees the exported card preview | The DOM renders as a static 1080×1080 card | Delight — "this looks good enough to post" | Cover art centered large, song title below, artist, action badges. drawnTo watermark subtle in corner. DM Sans typography carries the brand |
| 4. Shares to Instagram/Twitter/messages | Uses navigator.share() or saves image | Connection — "I just shared my music taste" | Native share sheet on iOS. Image is high quality, 1080×1080px, no pixelation |
| 5. Recipient opens the card | Sees the shared image in their feed | Curiosity — "what is drawnTo?" | Card includes subtle drawnTo URL/branding. The image is the invitation |

### Time-Horizon Design

- **5 seconds (visceral):** Near-black screen with a DM Sans wordmark and album art. The user knows: this is dark, this is about music, this is well-designed.
- **5 minutes (behavioral):** They've scrolled feed, switched tabs, logged a listen, opened a song page. Every action confirmed with a color fill and subtle press animation. No dead ends, no confusion.
- **5 years (reflective):** Their diary contains years of listening history. The journal aesthetic ages well — it's not trend-chasing. Dark, typographic, music-centered. Like a well-worn Moleskine.

## Premises

1. **The song detail page is the first rebuild target** — it has the worst mobile sizing and sets the visual template for album, artist, and user pages. One route wins, the rest follow.

2. **"Journal aesthetic" means deliberate density** — metadata and spacing shrink more aggressively than titles and art. The hierarchy stays: cover art and song titles keep presence; everything else compacts. `text-sm` (14px) for feed body text is an intentional mobile amendment to DESIGN.md's 16px body minimum.

3. **The PWA home screen is the design target** — 390×844px, notch-aware, no browser chrome. Safe area insets are first-class layout constraints, not afterthoughts.

4. **Shareable taste cards inform layout decisions now** — every card component (song page, diary entry, stat summary) should already be a balanced, exportable rectangle. The sharing feature becomes a one-tap action, not a separate render pipeline.

5. **The `md:` breakpoint stays the mobile/desktop divider** — mobile gets its own scale within `<768px`; desktop inherits the existing editorial scale. All existing `sm:` responsive overrides are replaced by the new mobile-first defaults: the mobile value becomes the base class, and `md:` restores the desktop value. No new breakpoints are introduced.

## Approaches Considered

### Approach A: Song Page First, Surgical Cuts
Rebuild one route (`song.$slug.tsx`) and its direct dependencies. New mobile scale: title `text-2xl` (24px), cover art `max-w-[240px]`. Everything else follows later.
- Effort: S (human: ~1 day / CC: ~30min)
- Risk: Low
- Pro: Fastest visible win — song page is the most broken
- Con: No design system work — each subsequent page gets custom one-off adjustments
- Con: Doesn't touch the daily feed/diary scroll experience

### Approach B: Mobile Design System + Song Page + Feed
Establish mobile-first design tokens, then rebuild song page and all feed cards (EntryCard, DiaryCard, CoalescedCard) together. One consistent scale across everything.
- Effort: M (human: ~3 days / CC: ~1hr)
- Risk: Medium
- Pro: Consistency from day one — every page aligns to the same mobile scale
- Pro: Feed density fix ships alongside the song page
- Pro: DESIGN.md gets a documented mobile amendment
- Con: Bigger surface area — more components touched at once
- Con: Higher regression risk on desktop if mobile tokens aren't scoped properly

### Approach C: Shareable Taste Cards as North Star
Build the 10x sharing feature first, using it as the design constraint. Every page component gets a "card view" that looks good as an exported image. The mobile layout IS the card, just interactive.
- Effort: L (human: ~5 days / CC: ~2hrs)
- Risk: Medium-High
- Pro: The dream feature ships — sharing is built in, not bolted on
- Pro: Forces visual discipline — if it looks good as a static card, it looks good on mobile
- Con: Blocks feed/shell fixes behind sharing infrastructure
- Con: Image export libraries have cross-platform quirks
- Con: Highest scope, highest risk

## Recommended Approach: 4-Phase Comprehensive Build

Synthesize the strengths of all three approaches into a phased rollout:

**Phase 1: Mobile Design System Foundation** — Tokens, scale, and component groundwork. No visual changes yet; this is infrastructure.

**Phase 2: Detail Pages** — Song, album, artist, and user profile pages get the mobile-native treatment. Cover art, typography, and layout rebalanced for 390px.

**Phase 3: Feed + Tab Views** — Entry cards, diary cards, coalesced cards, discover section, and bottom nav refinements. The daily scroll experience gets density.

**Phase 4: Shareable Taste Cards + Polish** — The 10x sharing feature, PWA manifest polish, splash page mobile audit, and journal creation flow audit. Gesture interactions are deferred to Phase 5 (follow-up).

### Phase 1: Mobile Design System Foundation

**Goal:** Establish shared mobile utility classes, the DESIGN.md amendment, and PWA manifest verification. No visual changes yet — this phase is infrastructure only.

**Work items:**

1. **Mobile component size utility classes** — add to `@layer utilities` in `src/styles.css`:
   ```css
   @media (max-width: 767px) {
     .mobile-art-detail { max-width: 240px; }
     .mobile-art-feed { width: 48px; height: 48px; }
     .mobile-art-discover { width: 88px; }
     .mobile-avatar { width: 28px; height: 28px; }
     .mobile-avatar-stack { width: 24px; height: 24px; }
   }
   ```
   These utility classes scope specific component sizes to mobile only. Desktop sizes are the existing Tailwind defaults. Applied as `className="mobile-art-detail"` — no `md:` restoration needed; the utility uses `@media (max-width: 767px)` so desktop ignores it.

2. **All other sizing uses standard responsive Tailwind classes directly in components.** No custom font tokens, no spacing utility classes, no `.mobile-text-*` classes. Every change in Phases 2-4 uses standard Tailwind responsive prefixes:
   - `text-2xl md:text-5xl` (song titles)
   - `gap-2 md:gap-3` (card spacing)
   - `w-[88px] md:w-[140px]` (discover cards)
   - `py-2.5 md:py-3` (card padding)

   This avoids a parallel naming system. All Tailwind responsive patterns are standard and self-documenting.

3. **DESIGN.md amendment** — add a `## Mobile Scale` section:
   - Body text minimum drops to 14px on mobile for feed density
   - Detail page titles drop to 24px
   - Touch targets stay at 44px minimum
   - Cover art drops to 240px max on detail pages
   - Feed thumbnails drop to 48px
   - Spacing compacts by ~25% across the board

4. **PWA manifest verification** — moved from Phase 4 to Phase 1. Verify `public/manifest.json` has `display: standalone`, correct theme color (`oklch(0.04 0.002 280)`), and 192px/512px icons. Add `<meta name="apple-mobile-web-app-capable" content="yes">` and `<meta name="apple-mobile-web-app-status-bar-style" content="black-translucent">` to `__root.tsx` `<head>` if missing. This ensures the PWA foundation is correct before any visual work that depends on `display: standalone` behavior.

**Files touched:**
- `src/styles.css` — component-size utility classes
- `DESIGN.md` — mobile scale amendment
- `src/routes/__root.tsx` — Apple meta tags
- `public/manifest.json` — verify PWA config

**Verification:** `bun run build` passes. Desktop renders unchanged. Mobile utility classes exist but aren't applied yet — zero visual change. Run `npm run test` — all existing tests must still pass (no class changes applied). PWA manifest verified correct.

### Phase 2: Detail Pages
